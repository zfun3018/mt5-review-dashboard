# A 计划渐进式体验与架构升级提案

## 状态与目标

- 状态：A0–A3 已完成并随 v1.0.2 发布，保留原功能与页面布局。
- 产品路线：继续维护现有 A 计划和 v1.x 版本。
- 目标：完整保留 A 计划现有功能、信息架构和页面布局，统一苹果风格玻璃 UI、ECharts 图表表达与筛选联动、仪表盘模块生命周期，并优化其实现边界。
- 本提案只面向桌面浏览器中的主要复盘流程；不规划移动端适配和原生桌面封装。
- 不迁移或读取本机交易数据；任何迁移和实现都必须先使用合成数据及测试数据库验证。

## 1. 现状与方案原则

A 计划已经具备 MT5 与国内期货工作区、SQLite 业务数据、Campaign/Position/Deal 关系、分析仪表盘、订单复盘、精选/随机/打卡、截图附件和平台隔离。前端使用 Python 标准库 HTTP、SQLite、原生 HTML/CSS/JavaScript 与 ES Modules；GridStack 和 ECharts 已用于仪表盘。该架构是继续演进的基线。

此次升级只改视觉表达和仪表盘内部架构，不改 A 计划的功能布局、不删减页面或功能，也不引入新的订单浏览模式。各阶段在 A 路径中小范围交付，能够独立验收和回退。仪表盘仍消费服务端指标；订单和复盘页继续保持现有布局、流程及 Campaign/Position/Deal 数据关系。任何实现都不得以 UI 更新为由隐藏或移除已有操作。

成功标准是：A 计划现有页面和功能原样保留；玻璃风格视觉统一且文字清晰；仪表盘筛选与图表数据一致；模块增删、布局编辑和异常恢复可靠；单模块故障不影响其余模块。技术栈升级本身不作为交付成果。

## 2. 本次升级采用的设计

| 设计方向 | A 计划实现方式 | 边界 |
| --- | --- | --- |
| 苹果风格玻璃 UI：统一圆角、背景模糊、层次阴影、药丸按钮和统一浮层 | 整理为共享 CSS tokens 与控件规范，分页面替换视觉样式 | 交互继续使用原生页面组件 |
| ECharts 图表表达、图表状态和图表与筛选的关系 | 保留现有 ECharts 实例，统一颜色、格式、空态、错误态、tooltip 与 resize 行为 | 指标定义和计算仍由服务端负责；ECharts 不是模块管理器 |
| 仪表盘模块注册、实例生命周期和故障隔离 | 在原生 ES Modules 中逐步建立轻量 registry/renderer 契约，管理模块类型、平台能力、数据需求、状态和 mount/update/resize/dispose | 继续使用现有 GridStack，不引入新的业务表 |
| 指标契约与样本质量 | 每项现有指标标明统计单位、事实时间、时区、定义版本、样本质量和下钻筛选 | 继续由服务端指标实现持有公式，前端不复算 |
| 仪表盘请求协调 | 共享当前筛选签名下的请求，取消过期请求并阻止旧响应覆盖新筛选结果 | 复用现有 API；不新增分析结果缓存表或第二份业务数据 |
| 模块状态与跨页面验收 | 统一加载、无数据、样本不足、警告、错误、有效值状态；用真实 owning workflow 做跨视图读取测试 | 状态是展示投影；测试不能只为每个页面单独 seed mock |
| 订单列表、复盘页面和现有功能布局 | 保留 A 计划现有布局与交互 | 本提案不包含订单 UI 架构替换或功能裁剪 |
| 实体所有权、指标规范、跨视图测试和模块状态契约 | 作为 A 计划所有新功能的设计与测试门禁 | 延续现有 Campaign/Position/Deal 和分析领域约束，不建立第二份业务数据 |

## 3. 本次升级范围边界

- 保持原生 HTML/CSS/JavaScript 与 ES Modules，不迁移前端框架。
- 复用现有 API；只有兼容问题经测试证明无法安全解决时，才单独评审接口版本化。
- 继续使用唯一的 SQLite 数据库与现有 v1.x 发布流水线。
- 本次不开发行情接入、成交点标记或 PA 画线，也不替换订单列表架构。
- 既有截图复盘和所有订单详情能力保持原样；本提案不改变行情来源或截图工作流。
- AI Skills、桌面客户端和 A 股行情不纳入本轮升级范围。

## 4. 目标架构

```text
现有 Python 标准库 HTTP 服务
  ├── 现有应用服务、平台适配器与指标定义
  └── SQLite（Campaign / Position / Deal / 复盘事实的唯一来源）
          ↓ 现有 API；必要时做兼容扩展
原生多页面与 ES Modules
  ├── 共享 UI tokens / 控件 / 玻璃层级
  ├── Dashboard：模块注册与 renderer host → ECharts 单模块实例
  ├── Orders：沿用 A 计划现有列表、详情和复盘布局
  └── Review：既有精选、随机、打卡与复盘字段
```

ECharts 只作为模块内部图表渲染依赖，不能直接读写 SQLite、重算业务指标或拥有交易字段。模块布局及用户偏好继续使用 A 计划既有配置路径；任何配置格式调整都必须保持旧配置可恢复，并明确版本迁移规则。

## 5. 分阶段方案与门禁

### A0：路线收敛与回退基线

- 将本提案作为 A 计划升级依据。
- 盘点 A 计划现有功能、页面布局、仪表盘布局、筛选行为、截图复盘和 API 行为，记录基准浏览器检查与核心测试。
- 维持现有 `/dashboard/`、`/orders/`、`/album/`、`/settings/` 路径；不改数据、不重写服务。
- 完成条件：现有行为清单、可回退点、API/数据归属和验收数据被文档化。

### A1：统一 UI 设计系统

- 统一色彩、背景材质、圆角、阴影、模糊、药丸按钮、输入框、下拉、弹窗、滚动条和焦点状态。
- 收敛到 `web/shared/css/` 的语义令牌与原生控件样式；先改共享外壳，再逐页迁移，避免一次性重做全部页面。
- 只改变颜色、材质、圆角、阴影、间距和控件外观，不改变页面结构、功能顺序、信息层级、订单列表或详情布局。
- 检查仪表盘、订单、复盘画册和设置中已有的加载、空、错误、选中和危险操作状态。
- 完成条件：共享弹层、下拉、按钮、滚动区使用统一令牌；文字对比清楚；页面布局、功能和键盘交互均与 A 计划基线一致。

### A2：修复并模块化现有仪表盘

- 先定位仪表盘模块重叠、删除后错位或尺寸异常的根因；写针对性失败测试后再修复现有 GridStack 生命周期、约束和保存/恢复路径。
- 在原生 ES Modules 中建立轻量模块 registry/renderer host；为每个现有模块声明稳定类型、平台支持、数据需求和 mount/update/resize/dispose 生命周期。
- 保留 A 计划现有模块、默认布局、顺序、尺寸和筛选行为；模块体系只改善注册、实例管理和故障隔离，不提供删减现有模块的理由。
- 保留当前服务端指标 API 与定义。ECharts 只负责单模块绘制；每个实例响应容器尺寸变化并在卸载时 dispose，失败时仅显示本模块错误。
- 图表必须与当前仪表盘筛选状态共享同一查询条件：时间范围、平台、账户等筛选变化后，各图表与指标卡同步更新；图表下钻使用相同筛选口径。
- 为每个模块建立指标契约：统计单位、事实时间字段、时区、公式/定义版本、样本质量规则、合成手算数据和下钻过滤条件。已有指标规范优先复用，不能在前端另造公式。
- 由 Dashboard Data Coordinator 根据规范化平台/账户/日期筛选生成稳定请求签名；同一筛选下共享一个分析响应，筛选变化时取消或作废旧请求，避免迟到响应覆盖当前状态。
- 模块状态统一为 `loading / empty / insufficient / warning / error / value`；单个模块转换失败或绘图失败时只影响该模块，并保证图表实例、监听器和请求生命周期可清理。
- 完成条件：A 计划所有现有模块均存在且布局保持一致；编辑、保存、刷新、恢复均稳定；单模块错误不影响其他模块；筛选值、图表值和服务端指标结果一致；合成数据可人工复算且样本状态符合指标契约。

### A3：整体验收与版本交付

- 执行后端测试、已有前端测试、仪表盘模块生命周期/筛选联动测试、跨页面 Campaign 测试和正式发布检查。
- 浏览器验收对比升级前后的 A 计划截图、路由、功能清单和关键操作，确认订单、复盘、设置布局没有改变或缩水。
- 只将已经通过验收的阶段并入 v1.x CHANGELOG；更新 README、项目说明和版本路线。

## 6. 数据与分析治理

- 业务事实由 SQLite 持有；Campaign 是订单与复盘的用户工作单位，Position/Deal 保持原有含义。
- 仪表盘模块只消费服务端分析结果，不在前端另算或保存收益、胜率、R、回撤等业务结果。
- 每个分析模块必须有指标定义：统计单位、事实时间、时区、公式版本、样本质量、可手算的合成数据和订单下钻筛选；模块 UI 的状态至少包括加载、无数据、样本不足、警告、错误和有效值。
- 仪表盘只在筛选签名变化时加载对应分析请求；重复筛选不得产生互相覆盖的请求，已取消/过期的响应不能更新任何模块。
- 模块布局属于用户展示偏好，不得复制 Campaign/订单数据；沿用现有布局持久化和恢复规则。
- 跨视图测试至少验证从拥有者工作流写入后，订单、画册/复盘、仪表盘下钻与相关 API 读取相同字段和值；分析测试还需验证同一合成 Campaign/Deal 数据的服务端指标、筛选结果和图表映射一致。页面各自独立 seed mock 不足以通过门禁。

## 7. 风险、取舍与回退

| 风险 | 控制 |
| --- | --- |
| 视觉升级覆盖现有交互或信息层级 | 按共享控件和页面分批迁移；每批保留截图/交互基线与回退提交 |
| 仪表盘修复继续叠加布局补丁 | 先复现根因和失败测试，再建立单一模块注册/生命周期路径；不并行保留旧、新布局编辑器 |
| 视觉升级演变成页面重排或功能裁剪 | 以 A 计划基线截图和功能清单为回归门禁；本提案明确禁止改变布局和删减功能 |
| 仪表盘模块重构意外改变数据口径 | 服务端指标定义保持不变；按筛选值和合成数据逐模块核对图表与指标结果 |
| 稳定性下降 | 不做整套前端框架迁移；逐阶段做窄改动、针对性测试、跨页面验证和 v1.x 发布门禁 |

A2 的根因与验证结果：仅 abort 不能保证底层请求忽略 `AbortSignal` 时旧筛选响应不会写回；仅有图表实例 dispose 也不能阻止一个图表绘制或销毁异常中断其他模块清理。现在两平台按加载代次忽略迟到响应；双平台模块注册表声明稳定 ID、宿主节点、数据需求与 metric key；模块状态映射服务端 `metric_meta` 并覆盖 loading、empty、insufficient、warning、error、value；接口整体失败会结束所有模块的 loading 状态；模块 renderer、ECharts 更新和销毁错误均被限制在所属模块。布局编辑器保存/恢复、默认布局和筛选状态已有自动化与浏览器覆盖，指标定义继续由服务端持有。

正式发布门禁运行当前页面与 A1 视觉 Demo 的桌面和 390px 浏览器用例。

订单与复盘页面布局、原有功能、服务端指标公式和业务数据均未因 A1/A2 改动；没有读取或迁移本机交易数据。本轮升级不包含行情接入和手动画线。
