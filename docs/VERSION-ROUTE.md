# 版本路线

本文件回答两个问题：项目现在处于什么状态，下一阶段准备解决什么问题。已经交付的内容见 [CHANGELOG](../CHANGELOG.md)，具体设计依据见 [架构与设计档案](superpowers/)。

## 当前状态

- 当前版本：`v1.0.1`；
- 当前阶段：双平台工作区、平台隔离数据模型、账户级仪表盘和订单复盘工作流已交付，进入兼容性、性能和发布维护阶段；
- 发布事实来源：根目录 `VERSION`；
- 正式交付方式：`vMAJOR.MINOR.PATCH` Git tag 对应一个 GitHub Release；
- 当前限制：服务没有登录认证，只适合本机或可信局域网；真实 MT5 EA 仍需在用户自己的 MetaEditor 环境中编译验证。
- v1.0.1 已完成账户/日期范围数据清理、国内期货固定周期指标、合约榜单名称和导入审计增强，并通过发布门禁；导入审计包含历史指纹迁移、已撤销批次清理、当前文件来源行号和同批次成交序号冲突保护。正式版本应由与 `VERSION` 一致的 `v1.0.1` tag 对应 GitHub Release。

## 版本规则

项目使用 SemVer：

| 版本段 | 适用情况 | 示例 |
| --- | --- | --- |
| MAJOR | 不兼容的数据、接口或运行方式变更 | `v1.0.0` |
| MINOR | 向后兼容的新功能或完整工作区能力 | `v0.7.0` |
| PATCH | 修复、兼容性改进、局部体验和文档改进 | `v0.6.21` |

正式 tag 必须使用 `v` 前缀，并且去掉前缀后与 `VERSION` 完全一致。普通提交不会自动产生 Release；只有推送版本 tag 才会触发 GitHub Release 工作流。

## 路线判断标准

一个功能进入路线前，需要说明：

- 它解决哪一个真实复盘问题；
- 它影响哪个工作区、数据模型或统计口径；
- 它是否需要迁移、备份或兼容处理；
- 它如何测试，桌面端和 390px 移动端是否需要回归；
- 它完成后应该进入哪个版本段。

只有完成实现、测试、文档和发布检查的内容，才会从“计划”进入 [CHANGELOG](../CHANGELOG.md)。

## 近期路线：维护和发布基础

目标是让每次更新都能被清楚检查、说明和交付。

- 使用 GitHub Release 作为正式版本更新入口；
- 保持 `VERSION`、路线、CHANGELOG 和 Release 标题一致；
- 完善数据库备份校验和失败恢复说明；
- 继续修复订单复盘、随机精选、打卡和局域网启动中的兼容性问题；
- 保持 Python、Node、语法、数据兼容和基准检查可重复运行。

完成条件：版本 tag 能自动通过版本校验和发布检查，GitHub Release 能生成清晰的变更说明；敏感本地数据不会进入提交或构建流程。

## 中期路线：数据管理和复盘效率

目标是减少手工整理数据的成本，同时保持现有统计口径稳定。

候选方向：

- 账户筛选，让多账户数据能够按账户查看；
- 导出公开统计或复盘摘要，且默认排除账户号、订单号和本机路径；
- 夏令时和交易时段配置，避免固定北京时间时段无法适配不同市场；
- SQLite 备份完整性校验、保留策略和恢复演练；
- 大数据量下的查询、分页和图片加载优化；
- 安装自检和首次启动检查，降低非专业用户的配置成本。

进入版本前必须先补充设计文档，明确导出字段、隐私过滤、时间口径、迁移策略和验收数据。

## 远期路线：桌面化和可选工程化

这些方向暂不承诺版本和日期，只有在需求和维护成本足够明确时才进入设计：

- Windows 桌面封装，保持程序目录和数据目录分离；
- 更完整的安装、升级和回滚体验；
- 当标准库 HTTP 或原生前端的维护成本明显增加时，再评估 FastAPI/Pydantic 或前端构建工具；
- 更大数据规模下的性能和归档策略。

远期方向不能以引入新技术为目标；必须先证明它能降低用户操作成本或维护风险。

## 发布节奏

不按固定日期承诺发布。一个版本在以下条件都满足后再发布：

1. 功能实现和相关测试完成；
2. 兼容性、迁移和隐私影响已说明；
3. README、路线和 CHANGELOG 已同步；
4. 完整发布检查通过；
5. 使用与 `VERSION` 一致的 tag 创建 GitHub Release。

具体操作见 [GitHub Release 发布指南](RELEASE-GUIDE.md)。
