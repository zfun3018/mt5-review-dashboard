# ADR-0001：采用模块化单体而非微服务

- 状态：接受
- 日期：2026-09-02
- 关联设计：[`docs/superpowers/specs/2026-09-02-architecture-redesign-design.md`](../superpowers/specs/2026-09-02-architecture-redesign-design.md)（ADR-001）

## 背景

本项目是单用户、本地优先（local-first）的 Windows 工具，运行时只有一个 Python 标准库 HTTP 服务和一个 SQLite 数据库。当前问题来自代码职责集中到少数超大文件造成的耦合，而不是部署规模或吞吐不足。

## 决策

保持单进程、单数据库部署，在进程内部建立四层结构和业务模块边界：

- 数据层 `app/data/`：SQLite 连接、迁移、仓储、写入命令、MT5 导入、截图与备份文件；
- 领域分析层 `app/domain/`：Campaign、R 倍数和统计公式；
- 应用调度层 `app/application/`：组合完整用例并统一响应字段；
- 表现层 `app/presentation/`：HTTP 路由、响应格式和兼容适配。

依赖只从外层指向内层，共享工具仅承载时间、格式化、校验等无业务归属的能力。

## 后果

### 正面

- 部署和排错保持简单，仍是一个进程、一个数据库、一次启动。
- 模块边界清晰后，页面级接口载荷和职责归属可被测试锁定。

### 负面

- 模块边界必须依靠测试和导入规则维持，不能依靠进程隔离。
- 需要额外的架构契约测试防止表现层绕过应用层直接访问存储。

## 被否方案

- **微服务**：引入网络、认证、部署和一致性成本，对单用户本地工具没有收益。
- **继续放任超大文件**：无法解决页面互相牵连和读取路径隐式写入的问题。
