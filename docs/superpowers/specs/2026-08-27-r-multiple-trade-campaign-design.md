# R 倍数与交易组合设计

## 状态

- 日期：2026-08-27
- 状态：已通过书面规格复核，批准进入实施计划
- 最后修订：2026-08-28，补充新增指标解释说明要求
- 目标版本：v0.5.0
- 影响范围：MT5 成交同步、SQLite 数据模型、订单流水、分析指标和相关测试

## 背景

当前系统把每个平仓成交近似视为一笔独立交易。这个模型无法正确表达以下实际操作：

- 同一持仓通过多个平仓成交逐步退出；
- 对冲账户中，同品种同方向的多次开仓形成多个独立持仓，但业务上属于同一次加仓交易；
- 一次交易组合只有一个最终结果，却可能在当前统计中被计算为多笔交易；
- 当前只把净盈亏严格等于零的交易视为打平，微赚和微亏会直接改变胜率和 Z 分数；
- 当前没有保存入场时的初始止损，无法计算基于计划风险的 R 倍数。

用户的交易规则已经明确：

- MT5 账户采用对冲模式，多次开仓显示为独立持仓；
- 同账户、同品种、同方向且持仓时间重叠的独立持仓，一定属于同一个加仓交易，不会同时运行两套独立策略；
- 每个独立持仓分别填写入场时采用的初始止损；
- 交易组合的总计划风险等于所有子持仓计划风险之和；
- 当前 R 计算暂不考虑手续费、隔夜利息和其他交易费用。

## 目标

1. 将成交、独立持仓和交易组合拆成清晰的数据层级。
2. 自动识别部分平仓和同方向重叠持仓形成的加仓组合。
3. 订单流水以交易组合为一行，展开后查看子持仓和成交。
4. 允许为每个独立持仓手动填写初始止损。
5. 任何子持仓缺少有效初始止损时，突出显示 R 数据不完整。
6. 以交易组合为单位计算 R、Scratch、双胜率、R 期望、SQN 和 Z 分数。
7. 保留现有现金盈亏按真实平仓日期归档的能力。
8. 迁移过程不丢失现有复盘文本、分类、自定义字段、截图、软删除状态或原始事件。

## 非目标

- 本阶段不把手续费、隔夜利息和费用计入 R。
- 本阶段不从 MT5 自动读取或追踪移动止损。
- 本阶段不计算最大不利波动或实际最大风险。
- 本阶段不支持跨品种组合为同一次交易。
- 本阶段不把同时存在的相反方向持仓合并。
- 本阶段不实现 Calmar 或 Sortino。
- 本阶段不引入第三方 Python、数据库或前端框架。

## 核心术语

### 成交 Deal

MT5 产生的一次实际成交。成交可以是开仓、加仓、部分平仓、完全平仓或反向成交。每个成交由 `deal_ticket` 唯一标识，并保留 `position_id`、成交方向、成交类型、手数、价格和时间。

### 独立持仓 Position

MT5 对冲账户中的一个独立 `position_id`。一个独立持仓可以包含多个开仓成交或多个平仓成交。初始止损填写在独立持仓上，而不是填写在每个平仓成交上。

### 交易组合 Campaign

订单流水和交易系统评估的复盘单位。相同账户、相同品种、相同方向的独立持仓，只要生命周期发生重叠，就自动归入同一个交易组合。

## 高层数据流

```text
MT5 全量 Deal 事件
        |
        v
规范化成交 deal_events
        |
        v
按 position_id 重建独立持仓 positions
        |
        v
按同账户 + 同品种 + 同方向 + 时间重叠自动组成 trade_campaigns
        |
        +--> 订单流水：一行一个 Campaign
        |
        +--> 现金统计：按 Deal 实际平仓日期
        |
        +--> 系统评估：按 Campaign 最终平仓日期
```

## 数据模型

### `deal_events`

保存规范化后的全部 MT5 成交，而不是只保存平仓成交。

字段：

| 字段 | 含义 |
| --- | --- |
| `deal_ticket` | 成交唯一标识，主键 |
| `account` | 账户标识 |
| `position_id` | MT5 持仓标识 |
| `order_ticket` | 关联订单标识 |
| `entry_kind` | `in`、`out`、`inout` 或 `out_by` |
| `side` | `long` 或 `short` |
| `volume` | 成交手数 |
| `price` | 成交价格 |
| `time_utc` | UTC 成交时间 |
| `time_msc` | 毫秒级成交时间，用于同秒事件排序 |
| `pnl` | MT5 返回的成交利润，不含本设计忽略的费用 |
| `raw_json` | 原始规范化载荷，便于追溯 |

`deal_ticket` 必须唯一，重复的 HTTP 和 JSONL 事件必须幂等处理。

### `positions`

保存从成交重建出的独立 MT5 持仓。

字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 本地稳定主键 |
| `account` | 账户标识 |
| `position_id` | MT5 持仓标识 |
| `campaign_id` | 所属交易组合 |
| `symbol` | 品种 |
| `side` | 方向 |
| `opened_at_utc` | 首次开仓时间 |
| `closed_at_utc` | 完全平仓时间，未平仓时为空 |
| `entry_volume` | 总开仓手数 |
| `weighted_entry_price` | 按手数加权的入场均价 |
| `initial_stop_price` | 用户复盘时填写的入场初始止损 |
| `risk_status` | `missing`、`invalid` 或 `complete` |
| `reconstruction_status` | `complete`、`legacy_estimated` 或 `incomplete` |
| `risk_updated_at` | 初始止损最后修改时间 |

同一账户内的 `position_id` 应唯一。初始止损只能由复盘输入修改，后续 MT5 移动止损不能覆盖它。多单止损必须低于该 Position 的每一个开仓成交价，空单止损必须高于该 Position 的每一个开仓成交价。

### `trade_campaigns`

保存订单流水和系统评价使用的交易组合。

字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 本地稳定主键 |
| `account` | 账户标识 |
| `symbol` | 品种 |
| `side` | 方向 |
| `started_at_utc` | 最早子持仓开仓时间 |
| `ended_at_utc` | 最后一个子持仓完全平仓时间 |
| `status` | `open` 或 `closed` |
| `review_text` | 组合级复盘文本 |
| `trade_type` | 组合级交易类型 |
| `strategy` | 组合级交易策略 |
| `deleted_at` | 组合级软删除状态 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

自定义字段和复盘分类应归属于 Campaign。子持仓仍可保留迁移前的复盘片段用于追溯，但不能在统计中当作多笔交易。

### 截图归属

本设计不扩展画册为多图功能。迁移时保留所有原始截图引用，并为 Campaign 选择一个主截图供现有订单流水和画册使用。展开 Campaign 时可以看到各子持仓原有截图。不得复制图片或丢弃旧引用。

## 自动重建独立持仓

后端按 `(account, position_id)` 对 Deal 分组，并按 `(time_msc, deal_ticket)` 排序。

规则：

1. `DEAL_ENTRY_IN` 增加该持仓的累计开仓量。
2. `DEAL_ENTRY_OUT` 减少剩余持仓量。
3. 剩余量大于零的退出成交是部分平仓。
4. 剩余量归零时，该独立持仓完全平仓。
5. `DEAL_ENTRY_INOUT` 必须拆解为旧方向退出和新方向进入，不能直接当作普通平仓。
6. `DEAL_ENTRY_OUT_BY` 保留关联关系，并作为对应持仓的退出成交处理。
7. 成交量不得因浮点误差变成极小的非零值，应根据品种手数步长或统一精度归零。

## 自动组合规则

### 基本规则

系统按 `(account, symbol, side)` 分组，然后对所有独立持仓的生命周期做区间扫描。

一个 Campaign 从该组累计活跃持仓数由零变为一开始，在累计活跃持仓数重新归零时结束。

因此：

- 第一笔独立持仓开始一个 Campaign；
- Campaign 尚未结束时建立的同方向独立持仓自动识别为加仓；
- 任一独立持仓内部的多次退出自动识别为部分平仓；
- 所有子持仓完全平仓后 Campaign 结束；
- 风险暴露归零之后的再次开仓属于新的 Campaign；
- 相反方向持仓不加入当前 Campaign，并产生数据冲突提示。

重叠关系具有传递性。若 A 与 B 重叠、B 与 C 重叠，即使 A 与 C 不直接重叠，A、B、C 仍属于同一个 Campaign，因为组合风险暴露从未归零。

### 同毫秒边界

必须使用 MT5 的毫秒时间并以成交票号作为稳定次序。若最终平仓先于下一次开仓，则创建新 Campaign；若下一次开仓先发生，则视为加仓。

### 手动修正

正常流程不要求用户确认或手动标记加仓。界面仍保留“拆分组合”能力，只用于数据缺失、历史重建错误或极少数异常。拆分操作必须可撤销，并保留原始 Deal 关系。

### Campaign 身份稳定性

Campaign 使用持久化本地 ID，不能在每次同步时根据时间范围重新生成。新 Position 到达时只扩展或合并受影响的 Campaign：

- 新 Position 与一个 Campaign 重叠时，加入该 Campaign；
- 迟到 Position 同时连接两个 Campaign 时，保留较早创建的 Campaign ID 作为主 ID，并迁移另一个 Campaign 的成员；
- 被合并 Campaign 的复盘文本、分类、自定义字段和截图作为来源片段保留，不能被覆盖；
- 手动拆分会保存显式分组覆盖规则，后续事件重放不能自动撤销用户修正。

## 初始止损与 R 计算

### 输入规则

- 每个独立 Position 分别填写一个 `initial_stop_price`。
- 多单初始止损必须低于该 Position 的每一个开仓成交价。
- 空单初始止损必须高于该 Position 的每一个开仓成交价。
- 初始止损等于入场价无效。
- 输入为空时状态为 `missing`。
- 输入在错误方向或无法解析时状态为 `invalid`。
- 复盘回填的初始止损是计划风险记录，不代表实际止损成交价或最大浮亏。

### Position 风险

当前忽略费用，并在同一品种内部使用“价格距离 × 手数”作为风险单位。

若一个 Position 有多个开仓成交，计划风险按开仓成交逐笔累加：

```text
position_risk = sum(
  entry_deal.volume * abs(entry_deal.price - position.initial_stop_price)
)
```

### Position 结果

完全平仓的 Position 使用加权入场均价汇总所有退出成交：

```text
long_result = sum(
  exit_deal.volume * (exit_deal.price - weighted_entry_price)
)

short_result = sum(
  exit_deal.volume * (weighted_entry_price - exit_deal.price)
)
```

退出总手数必须与开仓总手数一致，Position 才能进入最终 Campaign R。

### Campaign R

```text
campaign_total_risk = sum(position_risk)
campaign_total_result = sum(position_result)
campaign_r = campaign_total_result / campaign_total_risk
```

Campaign 内只包含同一品种，因此合约价值系数在分子和分母中抵消。费用不参与当前计算。

### R 完整性

Campaign 只有在以下条件全部满足时才返回 R：

1. Campaign 已完全平仓；
2. 所有 Position 的成交重建状态完整；
3. 所有 Position 都填写了有效初始止损；
4. 所有 Position 的退出总手数等于开仓总手数；
5. Campaign 总风险大于零。

任一条件不满足时：

- `campaign_r` 返回空值；
- 返回 `risk_positions_complete` 和 `risk_positions_total`；
- 返回明确的缺失或无效原因；
- 不能根据已填写的部分 Position 展示临时组合 R。

## Scratch 与指标口径

### Scratch 设置

增加可持久化的 `scratch_threshold_r`，默认值为 `0.15`。定义：

```text
abs(campaign_r) <= scratch_threshold_r
```

Scratch 阈值可以调整，但每个 Position 的 R 分母始终来自其初始止损，不能通过全局设置任意缩放。

### 双胜率

```text
净胜率 = R 完整盈利 Campaign 数 / (R 完整盈利 Campaign 数 + R 完整亏损 Campaign 数)

全样本胜率 = R 完整盈利 Campaign 数 / R 完整 Campaign 总数

Scratch 占比 = Scratch Campaign 数 / 已完成且 R 完整的 Campaign 数
```

R 不完整的 Campaign 不进入 Scratch、双胜率、E_R、SQN 或 R 版 Z 分数，并单独计入 R 数据覆盖率。界面同时保留基于现金盈亏正负的既有胜率，但必须命名为“现金胜率”，不能与 R 双胜率混用。

### R 期望

```text
E_R = sum(campaign_r) / R 完整 Campaign 数
```

Scratch Campaign 保留在 R 期望的分子和分母中。

### SQN

```text
SQN = mean(campaign_r) / sample_stddev(campaign_r) * sqrt(N)
```

- 使用样本标准差；
- `N < 30` 时显示“样本不足”，不输出质量等级；
- 标准差为零时不输出 SQN；
- 参考等级只能作为提示，不能直接判定系统合格或不合格。

### Z 分数

Z 分数按 Campaign 最终平仓时间排序，并排除 Scratch 和 R 不完整 Campaign。它不再按每个部分平仓成交生成胜负序列。

### Profit Factor

现有后端已经计算 Profit Factor。本设计只要求将其补充到合适的指标视图，不改变现有现金盈亏是否包含费用的既有口径。R 指标忽略费用与现有现金统计口径可以并存，界面必须分别命名，避免混淆。

## 时间归档规则

一次跨日 Campaign 同时存在两种统计日期：

### 现金实现统计

净盈亏、月历和按小时盈亏仍按每个退出 Deal 的实际成交时间归档。这样不会把前几天已经实现的盈亏全部移动到最后平仓日。

### 系统质量统计

胜率、Scratch、R、E_R、SQN、Z 分数和模式评估按 Campaign 的最终完全平仓时间归档。一个 Campaign 只计为一笔交易。

接口和界面必须清楚区分这两类统计，不能将 Deal 数量标为交易笔数。

## 前端设计

### 订单流水

订单流水默认一行一个 Campaign，至少展示：

- 品种和方向；
- Campaign 起止时间；
- 初始持仓和累计加仓信息；
- Position 数量；
- 部分平仓次数；
- Campaign 总盈亏；
- Campaign R 或 R 状态；
- 交易类型、策略和复盘状态。

有加仓或部分平仓的行显示简洁状态，例如：

```text
加仓 x2 · 分批平仓 x3
```

### 展开详情

展开 Campaign 后按时间列出所有 Position。每个 Position 展示：

- `position_id` 的隐私安全显示值；
- 入场时间、入场均价和开仓手数；
- 初始止损输入框；
- Position 风险状态；
- 该 Position 的所有退出成交。

### R 缺失高亮

- R 列固定显示状态，动态内容不得改变列宽。
- 完整状态显示格式化 R，例如 `+0.12R`。
- 缺失状态显示“待补初始止损”。
- 部分填写显示“R 不完整 1/2”。
- 无效输入显示“止损方向无效”。
- 使用颜色、文本和图标共同表达状态，不能只依赖颜色。
- 缺失状态可以给整行增加低强度边缘提示，但主要高亮限制在 R 单元格和对应 Position 输入框。

### 新增指标解释说明

订单流水、交易系统评估和交易模式评估中的每个新增指标都必须提供解释说明，不能只显示 `R`、`E_R`、`SQN` 等缩写。

- 订单流水的 R 列标题旁使用信息图标；鼠标、键盘聚焦和移动端点击均可打开说明。
- 系统评估和模式评估中的 `R`、Scratch、净胜率、全样本胜率、`E_R`、SQN、R 数据覆盖率都提供相同的说明入口。
- 说明内容至少包含指标中文名称、计算公式、当前样本数、当前 Scratch 阈值或 SQN 样本门槛、缺失原因和适用限制。
- R 说明明确指出分母来自组合内各 Position 的初始计划风险之和，不代表实际最大浮亏。
- Scratch 说明动态显示当前阈值，例如 `-0.15R 至 +0.15R`。
- SQN 说明明确显示 `N < 30` 时只报告样本不足，不提供质量等级。
- R 数据缺失时，说明列出缺少初始止损的 Position 数量，不显示基于部分数据的临时 R。
- 指标解释属于领域口径说明，使用一个共享的非卡片弹层或可展开说明区，避免为每个指标重复堆叠说明卡片。
- 所有说明入口必须具有可访问名称、焦点样式、Escape 关闭能力和点击外部关闭能力，不能只依赖鼠标悬停。

### 筛选和批量复盘

增加“仅看 R 缺失”筛选。筛选结果按 Campaign 展示，并在展开后自动定位第一个缺少初始止损的 Position。保存成功后立即重新计算 Campaign R 和相关分析，不要求整页刷新。

### 响应式要求

- 桌面端展开内容使用稳定列宽；
- 390px 移动端改为上下排列的 Position 明细；
- 不允许 R 状态文本造成水平溢出；
- 不把卡片嵌套在卡片中，Campaign 展开区使用普通明细布局。

## API 契约方向

接口职责固定如下：

| 能力 | 接口 |
| --- | --- |
| Campaign 列表 | `GET /api/campaigns`，返回一行所需汇总和 R 状态，不默认返回全部 Deal |
| Campaign 详情 | `GET /api/campaigns/{id}`，返回子 Position 和 Deal 明细 |
| 更新初始止损 | `PATCH /api/positions/{id}/initial-stop`，更新一个 Position 并返回重新计算后的 Campaign 摘要 |
| 分析设置 | `GET/PATCH /api/analysis-settings`，读取和更新 Scratch 阈值 |
| 分析结果 | `GET /api/analysis`，返回 Campaign 指标、R 覆盖率和既有现金统计 |

现有 `GET /api/trades` 在迁移期作为 Campaign 列表兼容入口，前端切换完成后再决定是否弃用。所有输入必须在服务端再次校验。前端校验只用于即时反馈。

## 现有数据迁移

### 迁移原则

- 新增 schema 版本，不破坏性覆盖真实交易数据；
- 迁移前创建本地数据库快照；
- 原始事件和现有交易记录保留用于追溯；
- 迁移必须可重复执行且不会重复创建 Deal、Position 或 Campaign；
- 不读取、提交或上传真实数据库、截图和原始事件。

### 历史 Position 重建

当前桥接只生成平仓事件，但每条记录包含 `position_id`、首次开仓时间、入场价、平仓手数和平仓价。对已完全平仓且事件完整的历史持仓，可以：

1. 先按 `(account, position_id)` 合并所有现有平仓记录；
2. 使用最早开仓时间和入场价建立历史 Position；
3. 使用所有平仓手数之和估计初始总手数；
4. 按 Position 生命周期重叠关系建立 Campaign；
5. 将重建状态标为 `legacy_estimated`，直到完整 MT5 Deal 历史完成回灌。

若历史事件不完整、持仓仍未关闭或开平仓数量无法闭合，标记为 `incomplete`，不计算 R。

### 完整历史回灌

升级后的 EA 和导入器应支持读取 MT5 历史中的所有 Deal，包括 `DEAL_ENTRY_IN`。完整 Deal 到达后，按唯一成交票号补齐历史，不覆盖用户已经填写的初始止损、复盘文本或分类。

### 复盘数据合并

多个旧交易记录合并为一个 Campaign 时：

- 不丢弃任何非空复盘文本；
- 原文本作为带来源的历史片段保留；
- Campaign 主复盘文本使用确定性规则初始化，之后由用户编辑；
- 分类冲突必须显式标记，不能静默选择；
- 所有旧截图引用继续有效；
- 已软删除旧记录迁移为排除的来源记录，不参与 Deal、Position 或 Campaign 指标；
- 排除旧记录导致成交量无法闭合时，Campaign 标记为 `incomplete`，不计算 R；
- 不能因为一个旧记录软删除而自动软删除包含其他有效 Position 的整个 Campaign。

## 同步改造

EA 不应继续只发送退出成交。每个 `TRADE_TRANSACTION_DEAL_ADD` 都应发送规范化 Deal 事件，并至少包含：

- 账户；
- `deal_ticket`；
- `position_id`；
- `order_ticket`；
- `DEAL_ENTRY`；
- `DEAL_TYPE`；
- 品种；
- 手数；
- 成交价；
- 秒和毫秒时间；
- 成交利润；
- 原始截图引用（如果该事件触发截图）。

HTTP 和 JSONL 继续双写。导入器仍以唯一事件指纹和 `deal_ticket` 保证幂等。

## 失败场景与处理

| 场景 | 处理 |
| --- | --- |
| Deal 重复到达 | 以 `deal_ticket` 幂等忽略或更新缺失字段 |
| 开仓事件晚于平仓事件导入 | Position 暂标不完整，补齐后重新计算 |
| Position 成交量无法闭合 | 不输出 Campaign R，显示数据不完整 |
| 初始止损缺失 | 高亮 R 状态并允许筛选 |
| 初始止损方向无效 | 返回 400、保留上一个有效值并给出明确错误；用户显式清空时才改为 `missing` |
| 同方向重叠 Position | 自动加入同一 Campaign |
| 相反方向同时持有 | 不合并，显示异常提示 |
| 同毫秒开平仓 | 使用毫秒时间和票号确定稳定顺序 |
| 历史分类冲突 | 保留全部来源并要求迁移审核 |
| Campaign 被软删除 | 同时排除其 Campaign 指标；原始 Deal 不物理删除 |
| 用户手动拆分 | 保留原始关系和可撤销记录，重新计算两个 Campaign |

## 性能与安全

- 继续使用 Python 标准库、SQLite 和原生前端。
- Deal 重建按时间排序，目标复杂度为 `O(N log N)`。
- 为 `deal_events(account, position_id, time_msc)`、`positions(campaign_id)` 和 `trade_campaigns(account, symbol, side, ended_at_utc)` 建立索引。
- Campaign 列表不能为每一行单独查询子 Deal，避免 N+1 查询。
- 初始止损、R 和交易数据继续只保存在本地 SQLite。
- 服务仍不得暴露到公网；本设计不引入认证能力。

## 验收标准

1. 同账户、同品种、同方向、生命周期重叠的独立 MT5 持仓自动显示为一个 Campaign。
2. 一个 Position 的多次退出不会增加交易笔数。
3. 一个 Campaign 的多个加仓 Position 不会增加系统评估交易笔数。
4. 每个 Position 可以独立填写并校验初始止损。
5. 任一 Position 缺少有效初始止损时，Campaign R 保持为空并明确高亮。
6. “仅看 R 缺失”可以快速定位所有待复盘 Campaign。
7. 完整 Campaign 按所有 Position 的计划风险之和计算一次 R。
8. Scratch、双胜率、E_R、SQN 和 Z 分数以 Campaign 为单位。
9. 现金实现统计仍按真实退出 Deal 日期归档。
10. 历史迁移不丢失复盘、分类、自定义字段、截图、删除状态和原始事件。
11. 不读取或提交任何真实交易数据库、截图、原始事件或本地配置。
12. 订单流水、系统评估和模式评估中的每个新增指标都有公式、阈值、样本和限制说明，并支持鼠标、键盘和移动端操作。

## 架构决策记录

### ADR-1：以 Campaign 作为复盘和系统评估单位

**决定：** 订单流水、胜率、R 和模式评估以 Campaign 为一笔交易，Deal 和 Position 仅作为可展开的组成部分。

**原因：** 部分平仓和加仓属于同一个交易决策，按 Deal 统计会重复交易笔数并扭曲胜率和 SQN。

**代价：** 现金实现日期和系统评估日期需要分开处理，前端和 API 必须明确命名。

### ADR-2：对同方向重叠持仓自动组合

**决定：** 在用户已确认的对冲账户交易规则下，相同账户、品种和方向的重叠 Position 自动加入同一个 Campaign。

**原因：** 用户不会对同品种同方向同时运行两个独立策略，重叠持仓等价于加仓。

**代价：** 仍需保留手动拆分能力处理历史缺失或异常数据。

### ADR-3：分别记录 Position 初始止损并累加总风险

**决定：** 每个 Position 单独填写初始止损，Campaign 总计划风险为所有 Position 计划风险之和。

**原因：** 对冲账户中的每次加仓是独立持仓，入场价格和计划止损可能不同；只使用首笔风险会低估整个组合风险。

**代价：** 任一子持仓未填写止损时，整个 Campaign R 都不可用。

### ADR-4：R 不完整时不显示部分估算

**决定：** 不根据已填写的部分 Position 显示临时 Campaign R。

**原因：** 部分风险分母会系统性高估 R，并误导 Scratch、E_R 和 SQN。

**代价：** 历史数据完成初始止损回填之前，R 覆盖率会较低。
