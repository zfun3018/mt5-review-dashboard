# 项目文档与 GitHub Releases 整理设计

## 状态

- 日期：2026-10-10
- 状态：已获用户批准，进入实施计划
- 目标：建立清晰的项目说明、技术文档、版本路线、历史记录和 GitHub Releases 发布流程
- 影响范围：项目文档、版本发布元数据、GitHub Actions；不改变应用代码、数据库结构和本地数据

## 背景

项目已经积累了较完整的功能说明、版本路线、架构决策和实施记录，但这些内容目前分散在根目录 README、子项目 README、版本路线、教程、计划和规格文档中。根目录 README 同时承担项目介绍、安装教程、隐私边界、AI 协作规则和完整变更日志，导致新用户、日常使用者和开发者都需要从一份过长文档中寻找信息。

版本路线还同时承担未来规划和历史变更记录。项目已有 `tools/check_release.py` 和 CI 检查，但没有明确规定正式版本必须通过 GitHub Release 交付，也没有自动校验 Git tag 与 `VERSION` 是否一致。

## 目标

1. 为不同读者提供明确的文档入口：新用户先看项目入口，使用者看运行说明，开发者看技术边界，维护者看路线和发布流程。
2. 将未来计划、历史变更和发布操作分离，避免同一文件不断变长并产生重复内容。
3. 将 `VERSION` 作为当前版本号的唯一事实来源，正式版本使用 `vMAJOR.MINOR.PATCH` Git tag 和 GitHub Release。
4. 推送版本 tag 时自动校验版本、运行发布检查并创建 GitHub Release。
5. 保留现有设计决策、实施计划和迁移文档作为项目档案，不改变其历史事实。
6. 保持敏感数据边界：不读取、不上传、不提交真实数据库、原始事件、截图、备份和本机配置。

## 非目标

- 不重构 Python、SQLite 或原生前端架构。
- 不引入第三方发布服务、包管理器或应用安装器。
- 不自动发布每一次普通提交；只有明确推送的版本 tag 才创建正式 Release。
- 不删除现有 ADR、历史计划和规格文档。
- 不把本地运行数据或当前机器路径写入公开文档。

## 文档信息架构

### 根目录入口

`README.md` 面向首次了解项目和希望快速运行的人，内容包括项目定位、核心能力、环境要求、最快启动方式、安全提示、文档地图和当前版本/Release 链接。历史版本明细不再放在这里。

### 项目技术说明

`docs/PROJECT-GUIDE.md` 说明系统组成、四个工作区、数据流、核心术语、后端分层、前端边界、数据目录和隐私规则。它解释“系统是什么、如何组成”，不重复完整安装步骤。

### 运行与开发说明

`mt5-review-system/README.md` 保留具体运行、MT5 EA、JSONL 回灌、接口和本地测试细节，并链接回根目录入口和项目技术说明。它不再维护独立的产品介绍和完整历史记录。

### 版本路线

`docs/VERSION-ROUTE.md` 只负责版本规则、当前状态、未来路线、版本范围和验收原则。未来计划按近期、中期、远期组织，计划项目说明目标和进入发布的条件，不伪装成已承诺日期。

### 历史变更

根目录 `CHANGELOG.md` 采用 Keep a Changelog 风格，承接现有 v0.1.0 至当前版本的事实记录。以后每个正式版本在此增加一节，GitHub Release 使用对应版本内容或自动生成的提交摘要作为补充。

### 发布操作

`docs/RELEASE-GUIDE.md` 面向非专业开发者，提供从确认改动、更新版本号、运行检查、提交、创建 tag 到检查 GitHub Release 的逐步流程，并明确普通提交、预发布版本和正式版本的区别。

### 历史设计档案

`docs/adr/`、`docs/plans/`、`docs/superpowers/specs/` 和 `docs/superpowers/plans/` 保持原位置，作为决策、设计和实施证据，不作为日常使用入口。

## GitHub Release 流程

1. 开发在普通分支提交功能和修复，版本号仍保持当前版本，除非准备正式发布。
2. 发布前更新根目录 `VERSION`、`docs/VERSION-ROUTE.md` 和 `CHANGELOG.md`，运行完整发布检查。
3. 提交发布元数据后创建与 `VERSION` 完全一致的 tag，例如 `VERSION` 为 `0.6.21` 时使用 `v0.6.21`。
4. 推送 tag 后，`.github/workflows/release.yml` 在 GitHub Actions 中执行：检出代码、校验 tag 与 `VERSION`、运行 `check_release.py --skip-browser`、创建 GitHub Release。
5. GitHub Release 使用 `release.yml` 的分类规则自动生成变更说明；维护者可在发布页面补充用户可读的重点说明。
6. Tag 与 `VERSION` 不一致、检查失败或同名 Release 已存在时，工作流失败，不创建正式 Release。

GitHub Actions 只需要仓库内置 `GITHUB_TOKEN` 的 `contents: write` 权限，不读取本地运行数据。发布工作流不执行 `git push`，只根据已经推送的 tag 创建 Release。

## 版本规则

- 当前版本号以根目录 `VERSION` 为准，格式为三段 SemVer 数字。
- 正式发布 tag 统一使用 `v` 前缀。
- `MAJOR`：不兼容的数据、接口或运行方式变更。
- `MINOR`：向后兼容的新功能或完整工作区能力。
- `PATCH`：修复、兼容性改进、文档和局部体验改进。
- 版本路线记录计划和范围，`CHANGELOG.md` 记录已完成内容，GitHub Release 记录实际交付内容。

## 验证要求

- 文档链接、版本号、tag 规则和 Release 工作流中的路径一致。
- 发布检查继续通过现有 Python、Node、语法、兼容性和基准测试；发布工作流默认跳过需要本地浏览器的门禁，以保证 GitHub runner 可重复执行。
- 不访问受保护的数据目录进行文档整理或发布检查。
- 现有项目测试不因文档和工作流变更而回归。
