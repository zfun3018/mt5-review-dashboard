# MT5 复盘仪表盘架构重构设计

状态：已接受
目标版本：v0.6.0
日期：2026-09-02

## 1. 背景与目标

项目经过多轮功能迭代后，核心业务仍然可用，后端测试也具备稳定基线，但代码职责逐渐集中到少数超大文件：前端主脚本同时管理仪表盘、订单、详情、配置与交互状态，后端存储模块同时承担数据库、迁移、业务计算、文件生命周期和接口数据组装。首页还会同时读取分析、Campaign 列表、设置和订单详情，导致页面之间互相牵连。

本次采用一次性交付式架构重构：新架构完成并通过验收后整体切换，开发内部仍按可验证的小阶段推进。目标不是从零重写交易逻辑，而是在保留现有数据、统计口径和用户功能的前提下建立清晰边界。

核心目标：

- 将复盘仪表盘、订单列表、复盘图册拆为三个独立页面。
- 使用统一的左侧导航、设计令牌和基础组件。
- 建立数据、领域分析、应用调度、表现层四层结构。
- 页面只读取自己需要的数据，减少首屏等待和重复计算。
- 保留全部历史数据、截图关联、复盘内容、分类和统计口径。
- 为后续 Windows 11 桌面封装预留稳定的运行与数据路径边界。

## 2. 范围

### 2.1 本次包含

- 重组后端模块和依赖方向。
- 重组前端页面、共享模块与页面状态。
- 拆分仪表盘、订单、图册和设置入口。
- 统一桌面和移动端导航与 UI 规范。
- 优化页面级接口载荷、服务端筛选与分页。
- 将 Campaign 重建从读取路径移到写入或显式修复路径。
- 建立数据兼容、迁移校验和回退机制。
- 更新测试、版本路线和维护文档。

### 2.2 本次不包含

- 不在本次发布中制作 Windows 安装包。
- 不更换 SQLite，不引入微服务。
- 不引入 React、Vue、Electron 或必须参与运行的前端构建工具。
- 不改变 Campaign、Position、R 倍数、收益和胜率的业务定义。
- 不迁移旧备份压缩包和原始 JSONL 归档。
- 不读取、上传或提交真实数据库、截图、事件、备份和本机配置。

Windows 桌面封装作为下一阶段交付，但本次必须完成程序目录与数据目录解耦、本机监听、安全启动和配置抽象，使后续封装不需要再次重构业务层。

## 3. 非功能要求

### 3.1 性能

- 本地普通数据规模下，页面主要内容应在 1 秒内可见。
- 使用 10,000 笔合成订单进行基准测试时，仪表盘和订单列表 API 的 p95 目标为 200ms；若当前标准库服务器环境无法稳定达到，必须记录基线、瓶颈和实测结果，不能以主观感觉验收。
- 仪表盘不得加载订单详情或完整 Campaign 列表。
- 订单列表默认每页 50 条，由服务端筛选和分页。
- 图册默认每页 24 条并保持图片懒加载。
- 读取 API 不得隐式执行完整 Campaign 重建或写入数据库。

### 3.2 可靠性与数据安全

- 现有 SQLite 数据必须原样兼容；不得通过清库、重新导入或人工复制字段完成升级。
- 任何数据库结构升级必须在事务中执行，并在升级前使用 SQLite Backup API 创建快照。
- 迁移失败时继续使用旧数据和旧版本，不能留下半迁移状态。
- 架构改造期间不移动真实数据目录。
- 服务默认只监听 `127.0.0.1`；局域网访问必须由用户显式开启。

### 3.3 可维护性

- 表现层不能直接执行 SQL，也不能直接导入存储实现。
- 应用层负责用例编排，但不复制领域公式。
- 领域层保持纯计算优先，可用普通字典或标准库数据类，不依赖 HTTP、文件路径和 SQLite 连接。
- 数据层只提供持久化、迁移、导入和文件生命周期能力，不生成 UI 文案。
- 每个页面只能加载自身入口模块，不能恢复为单一全局 `app.js`。

### 3.4 UI 与可访问性

- 桌面端使用固定左侧导航；窄屏使用可关闭的导航抽屉，不强行占用 390px 页面宽度。
- 页面不得出现横向溢出。
- 所有交互控件具备键盘焦点、加载、空数据、错误和禁用状态。
- 颜色对比满足 WCAG AA 的常用文本要求。
- 保持工作台式、克制、可扫描的信息密度，不使用营销页式大标题和装饰性背景。

## 4. 总体架构

采用模块化单体和四层依赖结构：

```text
MT5 EA / JSONL / 用户编辑
          |
          v
+------------------------------+
| 1. 数据层                    |
| SQLite、仓储、迁移、图片、导入 |
+--------------+---------------+
               |
               v
+------------------------------+
| 2. 领域分析层                |
| Campaign、R、统计、标签规则    |
+--------------+---------------+
               |
               v
+------------------------------+
| 3. 应用调度层                |
| 页面查询、命令、筛选、状态协调  |
+--------------+---------------+
               |
               v
+------------------------------+
| 4. 表现层                    |
| HTTP API、页面控制器、UI 组件   |
+------------------------------+
```

依赖只能向下。共享工具仅承载时间、格式化、校验等无业务归属的能力，不能成为新的杂物文件。

## 5. 页面与导航设计

### 5.1 应用外壳

桌面端左侧导航建议宽 224px，可折叠为 64px；主内容使用剩余宽度。导航项为：

1. 复盘仪表盘
2. 订单列表
3. 复盘图册
4. 设置

系统状态、备份和版本信息放在导航底部的设置区域，不再占用仪表盘顶部。导航使用本地打包的 Lucide 图标子集，不依赖公网 CDN。

在 720px 以下，左侧导航变为覆盖式抽屉，由菜单图标打开；关闭后内容使用完整宽度。当前页面标题和刷新操作保留在紧凑页面栏中。

### 5.2 复盘仪表盘

只负责分析和洞察：分析时间范围、系统评估、模式评估、收益曲线、月历、热力图和交易时段统计。页面不加载订单编辑器、字段管理器或 Campaign 详情。

筛选状态写入 URL 查询参数，使刷新和返回页面时保持一致。时间范围变化只刷新受影响区域，并取消已过期的请求。

### 5.3 订单列表

负责 Campaign 列表、Position 展开、初始止损、R 缺失筛选、截图、复盘和自定义字段编辑。桌面端使用主从布局，移动端列表和详情分步显示。

列表筛选与分页交给服务端。选中订单写入 URL，例如 `/orders/?campaign=...` 或兼容旧的 `trade` 参数。旧的 `/?trade=...` 链接重定向到订单页，避免画册历史链接失效。

### 5.4 复盘图册

保留当前日期分组、标签筛选、图片懒加载和大图预览。使用统一应用外壳和控件规范，但不改变图册的内容优先布局。

### 5.5 设置

承载分类管理、自定义字段管理、Scratch 阈值、系统状态、备份和将来的桌面运行设置。设置变更后由相关页面重新读取，而不是维护跨页面常驻全局状态。

## 6. 状态与调度

前端不建立覆盖全应用的单一状态对象。每个页面拥有自己的小型状态和控制器：

```text
URL / 用户操作
      |
      v
页面控制器 -> API 客户端 -> 应用服务
      |                         |
      +---- 状态更新 <----------+
                |
                v
             局部渲染
```

规则如下：

- 可分享、可返回的筛选和选中项进入 URL。
- 临时 UI 状态，如弹层、抽屉和加载标记，只保存在当前页面。
- 持久设置只以服务端结果为准，不在多个页面复制缓存。
- 搜索输入使用短防抖；新请求发出时取消同区域旧请求。
- 更新操作成功后只刷新受影响的数据，不重新加载整站。
- 页面卸载时清除定时器、事件订阅和待处理请求。

## 7. 接口与数据流

现有公共接口路径优先保持兼容，降低测试和历史链接风险。`/api/bootstrap` 保留为兼容入口，但新页面不再使用它。

推荐页面请求：

- 仪表盘：`GET /api/analysis`，按需读取月历参数和分析范围。
- 订单页：`GET /api/campaigns`、`GET /api/campaigns/{id}` 及现有编辑接口。
- 图册：`GET /api/review-album`。
- 设置页：分类、自定义字段、分析设置、状态和备份接口。

服务端路由只负责参数解析、调用应用服务和统一响应。应用服务组合仓储与领域计算。仓储负责 SQL 和序列化所需的原始数据，领域层不感知 HTTP。

### 7.1 写入数据流

```text
MT5 事件或用户编辑
  -> 参数校验与事件去重
  -> SQLite 事务写入
  -> 每批写入结束后重建受影响的 Position/Campaign
  -> 提交事务
  -> 返回新的领域结果
```

Campaign 重建不得继续隐藏在列表读取函数中。批量 JSONL 导入只在一批数据写完后重建一次；单条 API 写入只重建受影响范围。启动时仅在检测到模型版本不一致时执行显式修复。

### 7.2 读取数据流

```text
页面请求
  -> 路由参数校验
  -> 页面应用服务
  -> SQL 筛选/分页 + 领域计算
  -> 稳定响应对象
  -> 页面局部渲染
```

读取路径不得写数据库。订单与图册筛选应尽量下推到 SQL，避免先读取所有历史记录再在 Python 内分页。

## 8. 历史数据兼容与迁移

### 8.1 架构改造阶段

- 继续使用现有数据目录和 schema v4。
- 新仓储必须通过针对 v4 合成数据库的兼容测试。
- 若只增加索引，可以通过幂等迁移升级 schema；不得为了目录重组改变业务表含义。
- 迁移测试只使用合成数据和临时目录，不使用真实用户数据。

### 8.2 切换流程

1. 停止旧服务写入。
2. 使用 SQLite Backup API 创建迁移前快照。
3. 在副本或事务中执行 schema 迁移。
4. 校验 schema 版本、表完整性、外键关系和截图相对路径。
5. 对比迁移前后的订单数、Campaign 数、复盘数、自定义字段数及核心统计摘要。
6. 通过后启动新版本；失败则继续使用旧版本和原数据库。

### 8.3 Windows 软件阶段

首次启动时将正在使用的数据库、截图和配置复制到 `%LOCALAPPDATA%/MT5ReviewDashboard`，原目录保持不动。原始 JSONL 和历史备份压缩包不复制，继续在原目录归档。复制成功、校验通过并记录来源后才切换数据路径。

## 9. 错误处理与失败模式

| 失败场景 | 用户影响 | 处理方式 |
| --- | --- | --- |
| 数据库迁移失败 | 新版本无法读取 | 终止启动，保留原库并显示可操作错误 |
| Campaign 重建失败 | 订单与 R 数据可能不一致 | 写入事务回滚，不返回部分成功 |
| 页面请求失败 | 单一区域无数据 | 区域内错误状态和重试，不清空其他已加载区域 |
| 快速切换筛选 | 旧响应覆盖新结果 | 取消旧请求并校验请求序号 |
| 截图缺失 | 图册或详情无图 | 保留订单和补图入口，不删除记录 |
| 局域网误开启 | 本地数据暴露范围扩大 | 默认仅本机，设置页明确提示风险 |
| 旧链接访问 | 找不到订单 | 兼容重定向并保留查询参数 |

日志不得输出账户号、订单号、终端 ID、完整本机路径和截图内容。面向用户的错误信息使用普通中文，技术细节仅记录为脱敏诊断信息。

## 12. 架构决策记录

### ADR-001：采用模块化单体而非微服务

状态：接受。

背景：项目是单用户、本地优先的 Windows 工具，运行时只有一个 Python 服务和一个 SQLite 数据库。当前问题来自代码边界而非部署规模。

决定：保持单进程、单数据库部署，在进程内建立四层和业务模块边界。

后果：部署和排错保持简单；模块必须依靠测试和导入规则维持边界，不能依靠进程隔离。微服务因引入网络、认证、部署和一致性成本而不采用。

### ADR-002：前端采用原生多页面与 ES Modules

状态：接受。

背景：三个核心页面的加载内容和工作流明显不同，当前单一脚本和全局状态造成耦合。项目没有前端构建依赖。

决定：使用共享应用外壳加四个页面入口，每页拥有自己的控制器和状态，公共能力通过原生模块复用。

后果：页面首屏载荷和状态复杂度下降；共享体验需要通过设计令牌和组件规范保持一致。SPA 框架因迁移成本和当前规模不采用，继续在单页内打补丁也不采用。

### ADR-003：保持现有 SQLite 数据模型并进行兼容迁移

状态：接受。

背景：历史订单、截图、复盘和 Campaign/R 口径不可丢失，也不能要求用户人工导入。

决定：架构改造阶段继续使用现有数据库和 schema v4，仅通过版本化、事务化、可回退迁移增加必要索引或元数据。

后果：数据风险最低，但新仓储必须兼容历史字段。重建新数据库和转换到其他数据库均不采用。

### ADR-004：一次性交付，内部增量验证

状态：接受。

背景：用户选择统一切换的新版本，不希望长期维护新旧混合 UI；同时本项目涉及交易统计和历史数据，无法接受大爆炸式无检查开发。

决定：v0.6.0 作为一次性用户交付，开发过程设置八个内部检查点，每个检查点保持测试通过和可回退。

后果：用户最终获得统一版本；开发周期内不会发布部分页面。完全渐进式对外发布和无检查重写均不采用。

### ADR-005：Windows 封装后置，但现在建立兼容边界

状态：接受。

背景：最终希望成为 Windows 11 软件，但当前首要问题是架构耦合。过早封装会把路径、启动和状态问题固化进安装包。

决定：v0.6.0 完成路径配置、本机监听和模块边界；下一阶段再增加 WebView2 桌面壳与安装程序。

后果：本次仍以浏览器运行方式验收，但后续桌面化无需重写业务层。Electron 和本次同时交付安装包均不采用。

## 13. 完成标准

满足以下全部条件才可宣布架构改造完成：

- 三个核心页面独立运行并使用统一左侧导航。
- 设置和系统管理从仪表盘业务内容中分离。
- 前后端符合四层职责和依赖方向。
- 当前所有用户可见功能均有对应入口并通过回归测试。
- 历史 schema 兼容、迁移回退和数据一致性测试通过。
- 读取接口不再隐式重建 Campaign，页面不再加载无关数据。
- Python、Node 静态测试和浏览器验收全部通过。
- 桌面与 390px 视口无控制台错误或横向溢出。
- README、VERSION 和版本路线同步更新为 v0.6.0。
